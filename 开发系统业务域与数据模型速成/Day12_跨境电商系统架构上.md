```
└─────────────────────────────────────────────────┘
```

### 拆分原则

| 原则 | 说明 |
|------|------|
| 单一职责 | 每个服务只负责一个业务域 |
| 高内聚低耦合 | 域内逻辑紧密，域间通过API/MQ交互 |
| 独立部署 | 每个服务可独立开发、测试、部署 |
| 数据隔离 | 每个服务有自己的数据库，不跨库查询 |
| 限界上下文 | DDD方法论指导拆分边界 |

## 四、事件驱动架构

### 为什么需要事件驱动

```
问题: 同步调用链路过长

下单 → 扣库存 → 创建发货单 → 物流下单 → 发通知
  │       │         │           │          │
  └── 任一步失败，整条链路回滚，性能差

解决: 事件驱动 + 最终一致性

下单 → 发布"订单已创建"事件
              │
              ├──→ 库存服务: 监听 → 扣减库存
              ├──→ 物流服务: 监听 → 创建发货单
              └──→ 通知服务: 监听 → 发送通知

各服务独立消费，互不阻塞，失败可重试
```

### 事件总线设计

```
┌──────────┐     ┌──────────┐     ┌──────────┐
│ 订单服务  │────→│  MQ主题   │────→│ 库存服务  │
│ (发布者)  │     │          │     │ (消费者)  │
└──────────┘     │ order.   │     └──────────┘
                 │ created  │     ┌──────────┐
┌──────────┐     │          │────→│ 物流服务  │
│ 订单服务  │────→│ order.   │     │ (消费者)  │
│ (发布者)  │     │ paid     │     └──────────┘
└──────────┘     │          │     ┌──────────┐
                 │ order.   │────→│ 通知服务  │
                 │ shipped  │     │ (消费者)  │
                 └──────────┘     └──────────┘
```

### 核心事件定义

| 事件 | 发布者 | 消费者 | 说明 |
|------|--------|--------|------|
| order.created | 订单服务 | 库存/通知 | 新订单创建 |
| order.paid | 订单服务 | 库存/物流 | 付款成功 |
| order.shipped | 订单服务 | 通知/财务 | 已发货 |
| order.delivered | 订单服务 | 财务/通知 | 已妥投 |
| order.cancelled | 订单服务 | 库存/通知 | 订单取消 |
| inventory.out_of_stock | 库存服务 | 采购/通知 | 库存不足 |
| shipment.delivered | 物流服务 | 订单/财务 | 物流妥投 |

### 事件消息格式

## 五、多租户设计

### 隔离策略对比

| 策略 | 隔离级别 | 成本 | 复杂度 | 适用场景 |
|------|---------|------|--------|---------|
| 独立数据库 | 最高 | 最高 | 最低 | 大客户/数据安全要求高 |
| 共享数据库独立Schema | 中 | 中 | 中 | 中等规模 |
| 共享数据库行级隔离 | 最低 | 最低 | 最高 | SaaS多租户 |

### 行级隔离实现

```java
// 方案1: MyBatis-Plus 多租户插件
@Bean
public MybatisPlusInterceptor mybatisPlusInterceptor() {
    MybatisPlusInterceptor interceptor = new MybatisPlusInterceptor();
    interceptor.addInnerInterceptor(new TenantLineInnerInterceptor(
        new TenantLineHandler() {
            @Override
            public Expression getTenantId() {
                // 从上下文获取当前租户ID
                Long tenantId = TenantContext.getCurrentTenantId();
                return new LongValue(tenantId);
            }
            
            @Override
            public String getTenantIdColumn() {
                return "tenant_id";  // 租户字段名
            }
        }
    ));
    return interceptor;
}

// 方案2: 每次查询自动加 tenant_id 条件
// SELECT * FROM orders WHERE tenant_id = 1 AND status = 'PAID'
```

### 多租户在跨境电商的场景

```
租户 = 店铺 / 公司

公司A (tenant_id=1)
  ├── Amazon US 店铺1
  ├── Amazon UK 店铺2
  └── Shopee TH 店铺3

公司B (tenant_id=2)
  ├── Amazon US 店铺4
  └── TikTok Shop 店铺5

数据隔离:
  └── 公司A看不到公司B的订单/库存/财务
  └── 同一公司下的多店铺可共享库存
```

| 场景 | 选型 | 原因 |

## 七、面试/实战高频问题

1. **为什么用微服务而不是单体？**
   - 跨境电商业务域多且独立（商品/订单/库存/物流/财务），微服务允许独立开发部署，一个域出问题不影响其他。团队可按域分工。

2. **事件驱动如何保证消息不丢失？**
   - 生产者确认(publisher confirm) + 消费者手动ACK + 持久化 + 死信队列 + 补偿任务。关键业务用本地消息表保证"至少一次"投递。

3. **多租户行级隔离的性能影响？**
   - 每条查询都加tenant_id条件，需确保该字段有索引。大数据量下，可考虑按租户分表/分库，避免单表过大。

4. **Nacos vs Eureka怎么选？**
   - Nacos支持AP+CP模式切换，自带配置中心，与Spring Cloud Alibaba生态更契合。Eureka仅AP模式，已停止维护。

5. **微服务之间如何通信？**
   - 同步: OpenFeign (查询类，需即时响应)；异步: MQ (写操作、事件通知，解耦+削峰)。避免同步调用链路过长。
